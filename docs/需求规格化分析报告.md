## 1. 用户角色与数据访问范围

### 1.1 角色一览

| # | 角色 | 认证状态 | 归属范围 | 数据可见范围 |
|---|------|---------|---------|------------|
| R1 | **访客** (Visitor) | 未登录 | 无 | 全平台公开数据：首页、项目资源库、项目详情、活动组织指南、学校活动展示、公开排行榜、资料下载、学校入驻页。**不可见**任何学校内部数据（成绩、个人中心、工作台）。 |
| R2 | **学生** (Student) | 已登录 | 绑定一所学校 | 本校范围：本校活动、个人成绩、本校排行榜。可提交反馈和成绩申诉。**不可见**其他学校数据、不可见管理功能。 |
| R3 | **普通老师** (Teacher) | 已登录 | 绑定一所学校 | 本校范围：项目资源、下载资料、收藏项目、提交活动申请、查看本校活动。**不可见**其他学校数据。 |
| R4 | **学校管理员** (School Admin) | 已登录 | 管理一所学校 | **严格本校隔离**：管理本校活动、成绩、图片视频、账号（老师/学生）、排行榜、反馈。**不能管理其他学校任何数据**。 |
| R5 | **超级管理员** (Super Admin) | 已登录 | 全平台 | **全平台可见**：所有学校、所有项目资源、活动审核、内容审核、全平台排行榜、所有反馈建议、系统设置。 |

### 1.2 数据隔离规则

- **核心原则**: 不同学校之间的数据严格隔离。
- **实现方式**: 学生、普通老师、学校管理员的所有查询必须带 `school_id` 过滤。
- **超级管理员**: 可跨学校查看，但操作日志应记录其操作目标学校。
- **访客**: 只能访问明确标记为"公开"的数据。

### 1.3 角色层级关系

```
超级管理员 (平台级)
  └─ 学校管理员 (学校级，每校至少1人)
       ├─ 普通老师 (学校级，可有多个)
       └─ 学生 (学校级，可有多个)
访客 (无归属)
```

## 3. 核心业务实体及关系

### 3.1 实体清单

```
┌─────────────────────────────────────────────────────────────┐
│                    平台级实体 (Platform)                      │
├─────────────────────────────────────────────────────────────┤
│ School (学校)          — 入驻申请通过后创建                    │
│ ChallengeProject (挑战项目) — 超级管理员维护，全平台共享       │
│ ActivityGuide (活动组织指南) — 平台级资源                     │
│ DownloadMaterial (资料下载) — 平台级资源                      │
│ PlatformConfig (系统设置) — 超级管理员维护                    │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│               学校级实体 (必须包含 school_id)                  │
├─────────────────────────────────────────────────────────────┤
│ User (用户)            — 学生/老师/学校管理员                  │
│ Activity (活动)        — 学校创建的本校活动                    │
│ ActivityProject (活动项目) — 活动与挑战项目的关联配置           │
│ Score (成绩)           — 学生在活动项目中的成绩                 │
│ ScoreAppeal (成绩申诉)  — 学生对成绩的申诉                     │
│ Media (图片视频素材)    — 活动相关的图片视频                    │
│ RankingBoard (排行榜)  — 本校排行榜                           │
│ ActivityResult (活动成果) — 发布的活动总结成果                 │
│ Feedback (反馈建议)    — 用户提交的反馈                        │
│ ProjectFavorite (项目收藏) — 老师收藏的项目                   │
│ ActivityApplication (活动申请) — 老师提交的活动申请            │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│               跨学校/平台级关联实体                             │
├─────────────────────────────────────────────────────────────┤
│ SchoolRegistration (学校入驻申请) — 入驻前                     │
│ PlatformRanking (全平台排行榜) — 超级管理员发布                │
│ ContentReview (内容审核记录) — 超级管理员审核                  │
│ ActivityReview (活动审核) — 超级管理员审核                     │
│ AuditLog (操作日志) — 全平台                                  │
└─────────────────────────────────────────────────────────────┘
```

## 关键风险与建议

1. **学校数据隔离是第一优先级** — 所有 school_id 过滤必须在后端中间件层强制实现，不应依赖前端。
2. **成绩数据一致性** — 成绩录入→审核→排行→申诉→修改 形成闭环，需要仔细设计乐观锁或版本控制。
3. **项目资源版本化** — 如项目规则变更，历史活动的引用可能需要快照机制。
4. **权限矩阵必须在使用截图确认后再进入开发** — 权限模型一旦确定很难调整。建议使用带 OCR 的工具对 page_04_img0.png 做精确文本提取。
5. **导航方案需统一** — 页面 18 的深海军蓝独立导航与其他管理页面不一致，需在 SPEC-15（设计系统与UI规范）中确认最终方案。
6. **通知系统是横切关注点** — 建议从 Phase 0 就预留事件总线和通知接口，在各阶段逐步接入。
7. **设计系统差异可能是多版本混编** — 截图可能来自不同时期的原型设计，建议产品负责人确认以哪个版本为准。
