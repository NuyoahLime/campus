# ADR-003: Media 聚合边界

> **状态**: Accepted
> **日期**: 2026-07-14
> **决策范围**: Media 的聚合边界及双状态模型维护

---

## 1. 背景

素材拥有两个独立状态字段(`internal_status`和`public_status`)，存在校内停用触发平台下架的跨状态联动。需裁决Media是一个聚合维护双状态，还是拆分为校内和公开两个聚合。

## 4. 方案A: Media 单一聚合维护双状态

Media为聚合根，internal_status和public_status均为聚合内部字段，MediaReviewRecord为内部追加记录。

### 优点
- F4的联动(校内停用→平台下架)可单事务原子完成
- 双状态一致性在聚合内自然保证
- 模型简单，一个Media对象承载全部状态

### 缺点
- 校管和超管的权限边界在同一聚合内交织（校管改internal、超管改public、超管不得改internal）
- 如果后续平台公开审核逻辑复杂化，聚合职责可能膨胀
- 文件二进制不应属于领域聚合（应分离到存储层）

---

## 5. 方案B: 校内Media聚合 + 平台公开审核聚合分离

Media(校内)和MediaPublication(平台公开)为两个独立聚合。

### 优点
- 职责清晰：校管管理Media，超管管理MediaPublication
- 权限边界天然分离

### 缺点
- **F4联动跨聚合**：校内停用→平台下架需要跨聚合事务或最终一致性补偿
- 平台公开审核记录属于MediaPublication，但审核对象是Media的内容——引用关系复杂
- 增加了聚合数量和跨聚合协作

---

## 6. 方案比较

| 维度 | 方案A (单一聚合) | 方案B (拆分) |
|------|:--:|:--:|
| F4联动(校内停用→平台下架) | 单事务 | 跨聚合/最终一致 |
| 校管/超管权限分离 | 应用层判断字段 | 天然分离 |
| 模型复杂度 | 低 | 中 |
| 职责膨胀风险 | 中(公开逻辑复杂化时) | 低 |
| V1阶段适用性 | 高 | 中(过度设计风险) |

---

## 7. ADR_DECISION

**选择方案A: Media 为单一聚合根，双状态和审核记录均属聚合内部。**

V1阶段公开审核逻辑相对简单(单层审核)，方案A的事务简单性优于方案B的职责分离。如果后续平台公开审核演化为多级审核或独立发布流程，可通过ADR重新评估拆分。

| 项目 | 决策 |
|------|------|
| 聚合根 | Media |
| 聚合内部对象 | internal_status, public_status, MediaReviewRecord(校内), MediaReviewRecord(平台) |
| 外部引用 | Activity.id (必填), Uploader(User).id |
| 文件二进制 | **不属于领域聚合** — 存储为外部资源，Media仅保存引用(file_key/file_url) |

---

## 8. 单聚合验证

1. internal_status和public_status共享同一Media身份: ✅
2. 校内停用触发平台下架需原子更新: ✅ 同聚合内单事务保证
3. 校管只能操作internal_status相关流程(提交审核/停用/恢复)
4. 超管只能操作public_status相关流程(平台审核/强制下架)，不得修改internal_status
5. 应用层需强制执行上述字段级权限(聚合本身不感知角色)
6. 审核记录为聚合内部追加记录，实现时不需要每次完整加载历史
7. 文件二进制明确排除在领域聚合之外(Media仅保存file_key/file_url引用)
8. 聚合膨胀风险: 审核记录随素材生命周期增长，但每次追加一条，不修改已有记录。V1阶段每个素材的审核记录数量有限(校内1次+平台1次)，不构成膨胀问题

## 9. 聚合不变量

1. 上传人≠校内审核人
2. internal_status=校内审核通过 是提交平台公开审核的前置条件
3. 校内停用时若public_status=已公开 → 自动转为平台已下架
4. 恢复校内状态不自动恢复public_status
5. 超管不得修改internal_status
6. 校管不得修改public_status(只能提交/撤回)
7. activity_id必填，不可为空

---

## 9. 强一致操作

- 校内审核(审核通过/驳回): 单聚合事务
- **校内停用**: 如果public_status=已公开 → 同时更新public_status→平台已下架(**必须同事务**)
- 校内恢复: 仅更新internal_status (**不同时恢复public_status**)

## 10. 最终一致操作

- 被引用素材下架 → ActivityResult进入公开异常: 可最终一致
- 平台公开审核: Media聚合更新 + 审核记录追加

## 12. 权限边界

| 角色 | internal_status | public_status |
|------|:--:|:--:|
| 上传者(老师) | 提交审核 | 不可操作 |
| 校管(非上传者) | 审核/停用/恢复 | 提交公开/撤回 |
| 超管 | **禁止** | 审核/强制下架 |

## 14. 被拒绝方案

**方案B(拆分聚合)**: V1阶段过度设计。F4联动需要跨聚合事务，增加不必要的复杂性。如后续公开审核演化为独立发布流程，可通过新ADR重新评估。**暂拒绝**。

## 16. 决策后果

- 数据库: `media`表含`internal_status`和`public_status`两个独立列
- API: 校内操作和平台操作端点不同，但操作同一Media资源
- 权限中间件: 需区分校管和超管的字段级权限
