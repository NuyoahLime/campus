# ADR-006: 应用架构形态与模块组织

> **状态**: Accepted
> **日期**: 2026-07-14
> **决策范围**: 架构形态、模块划分、跨模块协作方式

---

## 背景

系统包含19个明确业务对象、17台状态机和5个已Accepted的聚合边界ADR。需要确定V1的架构形态以支持跨聚合事务、学校隔离和后续演进。

## FACT

- F1: 存在跨聚合原子业务结果(ADR-001 §9, ADR-002 §12)
- F2: 五角色权限矩阵(01 §1-3)
- F3: 学校数据严格隔离(01 §2.2)
- F4: V1规模约16个候选API模块
- F5: 无分布式部署的硬性需求

## 候选方案

### 方案A: 模块化单体 (推荐)
单一部署单元，内部按业务能力分模块，共享数据库。

### 方案B: 微服务
按模块拆分为独立服务。

### 方案C: 传统分层单体
Controller/Service/Repository全局横向分层。

---

## TECH_DECISION

**选择方案A: 模块化单体。**

- 模块组织: 按业务能力13个模块
- 模块验证: Spring Modulith (ArchUnit为补充候选)
- 模块内部: domain/application/infrastructure/interfaces
- 跨模块: 直接方法调用 + 领域事件接口

## 拒绝方案

- **方案B(微服务)**: V1规模不匹配；跨聚合事务需分布式事务；运维成本远超收益
- **方案C(传统分层)**: 模块边界弱；长期维护困难；无法按业务能力演进

## 后果

- 部署: 单JAR + 单数据库
- 后续拆分: 模块边界清晰时可提取为独立服务
- Spring Modulith不得改变已Accepted的聚合边界
- Spring Modulith不得强制跨模块异步
